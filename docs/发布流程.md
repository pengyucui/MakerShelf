# MakerShelf 发布流程

## 版本规则

稳定版本使用 `主版本.次版本`，需要补丁版本时使用 `主版本.次版本.修订版本`：

- 主版本：存在不兼容的数据格式、系统要求或核心行为变化。
- 次版本：向后兼容的新功能。
- 修订版本：向后兼容的错误修复和小幅体验改进。

Git 标签使用 `vX.Y` 或 `vX.Y.Z`，必须与 Xcode 工程中的 `MARKETING_VERSION` 一致。每次构建递增 `CURRENT_PROJECT_VERSION`。2.1 对应标签 `v2.1`、构建号 `12`。

## 公开源码范围

- `docs/` 只公开本文件和 `功能梳理.md`，其他本地资料由 `.gitignore` 排除。
- README 截图位于 `.github/images/`，Release 说明位于 `.github/release-notes/`。
- 保留原生工程所需资源、`ThirdParty/libwebp` 源码及许可。
- 已跟踪的内部资料使用 `git rm --cached` 取消跟踪，保留本地副本；此方式不清除历史提交。

## 脚本分工

| 入口 | 行为 | 环境 |
| --- | --- | --- |
| `bash scripts/package.sh` | 编译 Release 通用架构 App，生成 ZIP 和 SHA-256 | macOS、完整 Xcode |
| `bash scripts/release.sh` | 仅做本地检查并显示发布计划，不联网 | Bash 3.2 或更新版本、Git |
| `bash scripts/release.sh --push` | 检查远端标签，创建本地标签，推送分支和标签 | Git 推送权限、网络 |

脚本提示与注释使用中文，`scripts/lib/release-common.sh` 共用版本读取和错误处理。脚本不自动修改版本、不暂存或提交代码、不运行测试。打包脚本会编译当前工作区；公开安装包则由 GitHub Actions 从发布标签重新构建，不上传本机打包文件。

## 本地打包

在仓库根目录执行：

```bash
bash scripts/package.sh

# 指定输出位置；相对路径以执行命令时的当前目录为基准
bash scripts/package.sh --output ./dist/local

# 可额外要求版本完全匹配；不会替你修改工程版本
bash scripts/package.sh --version 2.1
```

默认产物位于 `dist/`：

```text
dist/
├── MakerShelf-版本-unsigned-macOS.zip
└── MakerShelf-版本-unsigned-macOS.zip.sha256
```

ZIP 内为 `MakerShelf-版本/` 文件夹，包含 `MakerShelf.app`、`LICENSE` 和 `NOTICE`。使用 Release 配置，同时构建 `arm64` 和 `x86_64`；打包前检查 App 的版本、构建号，以及主程序和登录辅助程序的两种架构。

每次使用独立临时构建目录，退出时只清理该目录；构建日志保存在 `build/logs/`。构建或打包失败时保留已有同名安装包；成功后替换输出目录中同版本的 ZIP 和校验文件。自定义输出目录应在仓库之外或已忽略的 `dist/` 内，避免将产物加入源码。

在产物目录验证下载完整性：

```bash
cd dist
shasum -a 256 -c MakerShelf-2.1-unsigned-macOS.zip.sha256
```

当前脚本生成未经过 Developer ID 签名和 Apple 公证的构建，文件名保留 `unsigned`。工程的登录辅助程序可能包含本机临时签名，这不代表 Developer ID 签名或公证。未来增加正式签名流程时，还需签名嵌套程序、启用 Hardened Runtime、提交 Apple 公证并装订票据，不能仅修改文件名。

## 准备下一版本

以 **2.2（构建 13）** 为例，版本仅作示例，脚本不会自动升级：

1. 合并目标版本代码到 `main`，检查公开源码不包含账号、Cookie、令牌、用户归档和个人 Xcode 状态。
2. 将 `MakerShelf.xcodeproj/project.pbxproj` 中 Debug / Release 的 `MARKETING_VERSION` 同步改为 `2.2`，`CURRENT_PROJECT_VERSION` 同步递增为 `13`。后续版本应继续递增构建号。
3. 将 CHANGELOG 的“未发布”改动归入 `## [2.2] - 实际发布日期`，更新底部版本链接和“未发布”比较链接。
4. 新建 `.github/release-notes/v2.2.md`，填写变更摘要、系统要求、安装方式、未签名说明与已知限制。可以参考已有的 `v2.0.md`，但必须更新内容、版本和链接。
5. 更新 README 的版本入口、功能状态及使用说明；新功能进入安装包后，移除相应“待发布”说明。
6. 自行完成必要的启动、登录、目录授权、导入、下载与升级验证，再整理并提交本次代码、脚本、工作流和发布资料。脚本不会代替人工验证或创建提交。

`v2.1` 是本次发布标签，后续版本不能复用它发布新的改动。两个脚本的 `--version` 参数只做一致性校验，不会更改文件。

## 发布推送

```bash
# 先做本地检查；工作区有改动或发布说明未准备好时会退出并给出原因
bash scripts/release.sh --version 2.2

# 准备完成后实际推送，触发自动发布
bash scripts/release.sh --version 2.2 --push

# 可选择已配置的远端和当前分支
bash scripts/release.sh --version 2.2 --remote origin --branch main --push
```

可通过 `bash scripts/package.sh --help` 和 `bash scripts/release.sh --help` 查看参数。

发布脚本要求当前分支与 `--branch` 一致，工作区无未提交或未跟踪文件；检查工程版本一致、构建号有效、发布说明非空、CHANGELOG 存在版本条目，以及工作流和打包脚本已提交。另检查 `docs/` 非公开资料、`prototype/`、根目录 `index.html`、构建目录和本机工具目录没有被 Git 跟踪。忽略的本地资料不影响发布，但脚本不代替完整的敏感信息检查。

默认模式不连接远端，因此“本地检查通过”不表示远端可推送。加 `--push` 后才会检查真实推送地址上的标签：标签已存在、网络失败或权限不足时直接退出；不会覆盖远端标签。允许复用指向同一提交的本地标签，便于网络失败后重试。

推送使用明确的分支和标签引用，原子提交到远端，不强制覆盖：分支非快进或标签冲突时，两项均不更新。远端需要支持原子推送，GitHub 支持此方式。脚本只推送本次标签，不附带其他本地标签。需要签名标签时，可先自行为同一提交创建签名标签，脚本会复用。

## GitHub Release 与失败处理

1. 推送 `v版本` 标签后，`.github/workflows/release.yml` 检查发布说明并调用 `scripts/package.sh --version 版本 --output dist`，校验标签和工程版本一致。
2. GitHub macOS Runner 重新构建，保存 Action 产物，并将 ZIP 和 SHA-256 上传到 Release。版本说明读取 `.github/release-notes/标签.md`。
3. 脚本提示“已推送”只代表 Git 操作完成，需继续查看 [GitHub Actions](https://github.com/pengyucui/MakerShelf/actions) 的构建结果；成功后检查 Release 下载链接和校验值。
4. 本地打包失败：查看 `build/logs/`；确认安装了完整 Xcode，且当前开发工具指向该 Xcode。若旧代码在 `Compile Login Helper` 阶段提示 `The following argument was not expected: -o`，检查是否误用了 Anaconda 的同名 `codesign`。当前工程已固定使用 `/usr/bin/codesign`，编译器通过 `/usr/bin/xcrun` 选择 Xcode 工具链；打包入口也使用 Apple 工具绝对路径，无需修改全局 PATH 或卸载 Anaconda。
5. 推送失败：本地标签保留，先检查远端是否已收到该标签。若未收到且提交未变，可直接重试；若要改代码，先确认远端不存在标签，再自行整理本地标签或使用新版本。脚本不会自动删除标签。
6. GitHub 构建因临时网络故障失败：在 Actions 中重新运行失败任务。若必须修改已发布标签对应的源码，应使用新版本，不能移动旧标签。原标签重新运行时，工作流会更新该 Release 的同名资产与说明。

禁止把本地 `dist/` 或 `build/` 目录提交到源码仓库；二进制只能作为 GitHub Release 资产上传。

发布整理使用脚本语法和工程配置静态检查；安装包由 GitHub Actions 构建。本地打包、真实数据验收与自动发布属于不同环节，发布成功不代表全部功能已通过人工验收。
