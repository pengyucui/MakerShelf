# MakerShelf 发布流程

## 版本规则

稳定版本使用 `主版本.次版本`，需要补丁版本时使用 `主版本.次版本.修订版本`：

- 主版本：存在不兼容的数据格式、系统要求或核心行为变化。
- 次版本：向后兼容的新功能。
- 修订版本：向后兼容的错误修复和小幅体验改进。

Git 标签使用 `vX.Y` 或 `vX.Y.Z`，必须与 Xcode 工程中的 `MARKETING_VERSION` 一致。每次构建递增 `CURRENT_PROJECT_VERSION`。2.0 对应标签 `v2.0`、构建号 `11`。

## 公开源码范围

- `docs/` 只公开本文件和 `功能梳理.md`，其他本地资料由 `.gitignore` 排除。
- README 截图位于 `.github/images/`，Release 说明位于 `.github/release-notes/`。
- 保留原生工程所需资源、`ThirdParty/libwebp` 源码及许可。
- 已跟踪的内部资料使用 `git rm --cached` 取消跟踪，保留本地副本；此方式不清除历史提交。

## 发布前检查

1. 确认工作区无账号、Cookie、令牌、用户归档和个人 Xcode 状态。
2. 更新 `CHANGELOG.md`，将“未发布”内容归入目标版本并写明日期。
3. 更新 README 中的系统要求、功能边界和安装方式。
4. 使用 Release 配置生成通用架构 App，并确认版本号和 Bundle ID。
5. 使用 Apple Developer ID 签名，启用 Hardened Runtime，提交 Apple 公证并装订公证票据。
6. 在干净的 macOS 用户环境中验证首次启动、登录、目录授权、导入、下载和升级。

## 发布资产

正式二进制文件名使用 `MakerShelf-X.Y-macOS.zip`。同时生成：

```sh
shasum -a 256 MakerShelf-X.Y-macOS.zip > MakerShelf-X.Y-macOS.zip.sha256
```

Release 至少包含变更摘要、系统要求、安装方法、已知限制、ZIP 和 SHA-256 文件。ZIP 内必须同时包含 `LICENSE` 与 `NOTICE`。未经 Developer ID 签名与 Apple 公证的构建不得标记为正式安装包；可以作为公开的未签名资产，但文件名和说明必须明确标注。

## GitHub Release

1. 合并目标版本代码到 `main`。
2. 创建并推送标签，例如 `v2.0`。
3. `.github/workflows/release.yml` 校验标签与工程版本，然后在 GitHub macOS Runner 上重新构建。
4. Action 打包 `MakerShelf-版本-unsigned-macOS.zip`、生成 SHA-256，并读取 `.github/release-notes/标签.md` 创建 Release。
5. 未配置 Developer ID 和 Apple 公证前，Action 产物明确标记为 `unsigned`；不得改名冒充正式签名安装包。
6. 发布后检查标签、源码归档、下载链接和校验值，再更新“未发布”比较链接。

禁止把本地 `dist/` 或 `build/` 目录提交到源码仓库；二进制只能作为 GitHub Release 资产上传。
